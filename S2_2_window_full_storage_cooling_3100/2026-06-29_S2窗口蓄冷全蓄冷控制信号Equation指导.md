分析日期：2026-06-29  
分析对象：`S2/Project11.dck`、`S2/load_year_15min_new.csv`、`S2/CO2_window.csv`、`S2/analysis_report.md`  
系统类型：集中供冷水蓄冷系统，窗口目标驱动的全蓄冷策略。  
审查立场：以建筑与能源系统研究者、审稿人的角度，重点审查控制逻辑是否物理一致、设备信号是否互斥、Type11f 分流方向是否正确、回水路径是否闭合，以及策略是否便于论文解释与复现实验。

## 1. 策略边界与核心权衡

S2 与传统固定夜间蓄冷策略不同。这里不再把蓄冷限定在 `0:00-8:00`，而是由外部输入的窗口信号 `Window_time` 决定。只要处于工作日且窗口信号为 1，就允许冷机1和冷机2联合给蓄冷罐蓄冷；若水箱已满，则停止蓄冷；若仍处于窗口内且水箱因散热、混合或负荷扰动导致蓄冷量下降，则再补冷。

控制策略可概括为四条：

1. 工作日窗口内，冷机1+冷机2只负责蓄冷，不直接承担负荷。
2. 工作日窗口内若同时存在负荷，由冷机3直供负荷，水箱不释冷。
3. 非窗口内若有负荷，优先由蓄冷罐释冷。
4. 非窗口内若有负荷且水箱冷量不足，冷机3直供负荷，冷机1/2仍关闭。

审稿意见：  
“满罐停机、SOC 下降到一定程度再补冷”是典型迟滞控制。普通 TRNSYS Equation 是代数表达式，没有记忆功能，不能严格表达“上一步已经启动/停止”的锁存状态。若论文要严谨，应使用 Type2 差分控制器、Type93 记忆单元，或等价的状态控制模块。本文给出一个可直接落地的 Equation 近似版本，并在后文说明更严谨的实现建议。

## 3. Type11f 分流阀出口方向

你给出的 Type11f 关系是：

```text
flow2 = flow * gam
flow1 = flow * (1.d0 - gam)
Output1 = tin
Output2 = flow1
Output3 = tin
Output4 = flow2
```

因此：

- `outlet1` 对应 `Output1/Output2`，流量为 `flow*(1-gam)`。
- `outlet2` 对应 `Output3/Output4`，流量为 `flow*gam`。
- `gam=0` 表示全部走 outlet1。
- `gam=1` 表示全部走 outlet2。
- `gam=0.5` 表示两个出口各 50%。

### 3.1 S2 中两个关键分流阀

| 分流阀 | Unit | 入口 | outlet1 | outlet2 | 控制意义 |
|---|---:|---|---|---|---|
| 分流阀-2 | 14 | 管道-4，即蓄冷罐 Outlet-2 回冷机侧主管 | 冷机1 | 冷机2 | 蓄冷时 `gam14=0.5`，两台冷机均分回水 |
| 分流阀-3 | 29 | 回水水泵 Unit33 出口 | 蓄冷罐 Port-1 | 冷机3 冷冻水入口 | 水箱释冷时 `gam29=0`；冷机3直供时 `gam29=1` |

这里尤其要避免一个常见错误：  
冷机3直供时，Unit29 必须走 outlet2，因此 `gam29=1`；水箱释冷时，Unit29 必须走 outlet1 回蓄冷罐，因此 `gam29=0`。

## 4. 窗口信号与输入信号说明

### 4.1 负荷输入

`load_year_15min_new.csv` 由 Unit22 读取：

```text
LoadRaw = [22,1]
```

当前负荷数据量纲按 `kJ/h` 处理，建议在控制中统一折算为 kW：

```text
LoadKW = LoadRaw/3600
```

### 4.2 窗口输入

`analysis_report.md` 说明窗口文件按每日低碳窗口标记生成，`CO2_window.csv` 是三列文件：

```text
原始碳因子或标记相关列, 修正前标记, 修正后标记
```

S2 中 Unit40 读取 `CO2_window.csv`，并设置为读取 3 个输出。因此推荐：

```text
Window_time_raw = [40,3]
```

理由：第 3 列通常代表“连续性修正后的窗口标记”，更适合作为最终控制信号。若你另有明确约定，确认 `Window_time` 已在 TRNSYS 中作为 0/1 信号输入即可。

## 5. 推荐 Equation 公式

以下公式以“窗口内蓄冷、窗口内负荷由冷机3直供、窗口外优先水箱释冷”为目标。每条公式后的注释都说明了物理含义。

```text
T_cold_sp = 4
! 冷水目标温度；冷机1/2蓄冷和冷机3直供均可采用 4 C 作为 CHW Set Point。

T_warm_ref = 12
! 暖态回水参考温度；用于定义蓄冷罐接近放空时的温度基准。

dT_dead = 1
! 温度判断死区；避免节点温度在单个时间步内小幅波动造成频繁切换。

LoadRaw = [22,1]
! Unit22 读取的原始负荷；当前 S2 中按 kJ/h 处理。

LoadKW = LoadRaw/3600
! 将负荷由 kJ/h 折算为 kW，便于设置有效负荷阈值。

HasLoad = gt(LoadKW,5)
! 有效负荷判断；低于 5 kW 视为无制冷需求或数值噪声。

Window_time_raw = [40,3]
! Unit40 读取 CO2_window.csv 的第 3 列；建议使用修正后的 0/1 窗口信号。

Window_time = max(0,min(1,Window_time_raw))
! 将窗口信号限制在 0-1，防止文件读入异常值影响控制。

IsWindow = gt(Window_time,0.5)
! 将窗口信号转为布尔变量；1 表示当前时间步为蓄冷窗口。

T_tank_avg = [7,5]
! Type534 输出 5，水箱平均温度；用于估算整体蓄冷状态。

T_node_top = [7,18]
! 水箱冷端/顶部代表节点；用于判断冷区是否已经形成。

T_node_mid = [7,30]
! 水箱中部节点；用于判断温跃层是否推进到中部。

T_node_bot = [7,42]
! 水箱暖端/底部代表节点；用于判断释冷是否接近耗尽。

SOC_raw = (T_warm_ref-T_tank_avg)/(T_warm_ref-T_cold_sp)
! 按平均温度估算蓄冷状态；越接近 4 C，SOC 越高。

SOC = max(0,min(1,SOC_raw))
! 限幅后的蓄冷状态；0=接近空罐，1=接近满罐。

TankFull = lt(T_node_top,T_cold_sp+dT_dead)*lt(T_node_mid,T_cold_sp+1.5)
! 顶部和中部均接近冷水温度时，认为水箱已基本蓄满。

TankEmpty = gt(T_node_bot,T_warm_ref-dT_dead)*gt(T_node_mid,T_warm_ref-3)
! 底部和中部均偏暖时，认为水箱可用冷量不足。

SOC_DischargeMin = 0.10
! SOC 低于 10% 时禁止继续优先释冷，避免供水温度失控。

SOC_ChargeStop = 0.985
! 代数近似版的蓄冷停止阈值；接近满罐时停止。

SOC_Recharge = 0.92
! 严格迟滞版的补冷触发阈值；满罐后若 SOC 降到该值以下才重新补冷。

Chg_bySOC_alg = lt(SOC,SOC_ChargeStop)*(1-TankFull)
! 无记忆 Equation 近似版：水箱未接近满罐且节点未满时允许蓄冷。

Dch_bySOC = gt(SOC,SOC_DischargeMin)*(1-TankEmpty)
! 释冷许可：水箱 SOC 足够且未达到空罐节点判据时允许释冷。

HourOfDay = time-24*int(time/24)
! 当前仿真时刻在一天内的小时数。

DayNum = int(time/24)
! 从 TRNSYS 绝对时间计算日序号。

WeekIndex0 = DayNum-7*int(DayNum/7)
! 未校准周内索引，0-6 循环。

WeekdayOffset = 0
! 星期偏移量；必须按负荷文件首日实际星期校准。

RawWeekIndex = WeekIndex0+WeekdayOffset
! 加入星期偏移后的周内索引。

Weekday = RawWeekIndex-7*int(RawWeekIndex/7)
! 归一化周内索引；建议约定 0=周一，1=周二，...，6=周日。

IsWorkday = lt(Weekday,5)
! 工作日判断；周一至周五为 1，周六周日为 0。

IsLoadTime = ge(HourOfDay,8)*lt(HourOfDay,22)
! 负荷时间判断；工作日 8:00-22:00 才允许出现供冷需求。

LoadWindow = IsWorkday*IsLoadTime*HasLoad
! 有效供冷需求窗口；周末、非 8-22、无负荷时均为 0。

ChargeWindow = IsWorkday*IsWindow
! 工作日窗口蓄冷许可；不再固定 0-8 点，只看外部窗口信号。

ChargeMode = ChargeWindow*Chg_bySOC_alg
! 蓄冷模式：工作日窗口内且水箱未满时，冷机1/2联合蓄冷。

Direct3_Window = ChargeWindow*LoadWindow
! 窗口内若有负荷，负荷由冷机3直供；此时不使用水箱释冷。

TankMode = (1-ChargeWindow)*LoadWindow*Dch_bySOC
! 非窗口内有负荷且水箱可用时，优先由水箱释冷。

Direct3_Backup = (1-ChargeWindow)*LoadWindow*(1-Dch_bySOC)
! 非窗口内有负荷但水箱冷量不足时，冷机3作为备用直供。

Direct3Mode = min(1,Direct3_Window+Direct3_Backup)
! 冷机3直供总模式；包括窗口内带负荷直供和非窗口水箱不足直供。

OffMode = (1-min(1,ChargeMode+TankMode+Direct3Mode))
! 停机检查变量；不直接控制设备，用于确认是否没有任何运行模式。
```

## 8. 三种典型运行路径核对

### 8.1 工作日窗口内、无负荷、水箱未满

运行：

```text
冷机1/2 + 供冷水泵1/2 + 蓄冷水泵32 + 冷却塔1/2 + 冷却水泵1/2
```

路径：

```text
冷机1/2 -> 供冷水泵1/2 -> 合流阀 Unit15 -> 管道-1 Unit25
-> 蓄冷水泵 Unit32 -> 蓄冷罐 Port-2
-> 蓄冷罐 Outlet-2 -> 管道-4 Unit31
-> 分流阀-2 Unit14 -> 冷机1/2
```

控制：

- `ChargeMode=1`
- `Direct3Mode=0`
- `TankMode=0`
- `Gamma14=0.5`
- `Gamma29` 无主流量，置 0

### 8.2 工作日窗口内、有负荷、水箱未满

此时存在两个并行回路：冷机1/2给水箱蓄冷，冷机3给负荷直供。

蓄冷回路：

```text
冷机1/2 -> 供冷水泵1/2 -> 合流阀 Unit15 -> 管道-1 Unit25
-> 蓄冷水泵 Unit32 -> 蓄冷罐 -> 管道-4 Unit31
-> 分流阀-2 Unit14 -> 冷机1/2
```

负荷直供回路：

```text
冷机3 -> 供冷水泵-3 Unit34 -> 合流阀-2 Unit26
-> 供冷总管 Unit5 -> 负荷需求端 Unit4
-> 回水总管 Unit28 -> 回水水泵 Unit33
-> 分流阀-3 Unit29 outlet2 -> 冷机3
```

控制：

- `ChargeMode=1`
- `Direct3Mode=1`
- `TankMode=0`
- `Gamma14=0.5`
- `Gamma29=1`

### 8.3 非窗口、有负荷、水箱冷量充足

运行：

```text
蓄冷罐 + 释冷水泵6 + 回水水泵33
```

路径：

```text
蓄冷罐 Outlet-1 -> 释冷水泵 Unit6 -> 合流阀-2 Unit26
-> 供冷总管 Unit5 -> 负荷需求端 Unit4
-> 回水总管 Unit28 -> 回水水泵 Unit33
-> 分流阀-3 Unit29 outlet1 -> 蓄冷罐 Port-1
```

控制：

- `TankMode=1`
- `Direct3Mode=0`
- `ChargeMode=0`
- `Gamma29=0`

### 8.4 非窗口、有负荷、水箱冷量不足

运行：

```text
冷机3 + 供冷水泵3 + 冷却塔3 + 冷却水泵3 + 回水水泵33
```

路径：

```text
冷机3 -> 供冷水泵-3 Unit34 -> 合流阀-2 Unit26
-> 供冷总管 Unit5 -> 负荷需求端 Unit4
-> 回水总管 Unit28 -> 回水水泵 Unit33
-> 分流阀-3 Unit29 outlet2 -> 冷机3
```

控制：

- `Direct3Mode=1`
- `TankMode=0`
- `ChargeMode=0`
- `Gamma29=1`

## 9. 严格迟滞控制建议

若坚持“水箱提前蓄满后停止，窗口内 SOC 下降到一定程度再补冷”，建议不要只依赖 `Chg_bySOC_alg`。更严谨的逻辑应是：

```text
ChargeStart = ChargeWindow*lt(SOC,SOC_Recharge)*(1-TankFull)
! 满罐后，只有 SOC 下降到 0.92 以下才重新触发补冷。

ChargeStop = TankFull+gt(SOC,SOC_ChargeStop)
! 达到节点满罐或 SOC 接近 0.985 时停止补冷。
```

然后用有状态控制模块实现：

```text
ChargeLatch = 1  当 ChargeStart=1
ChargeLatch = 0  当 ChargeStop=1 或 ChargeWindow=0
ChargeMode = ChargeWindow*ChargeLatch
```

审稿意见：  
如果论文要讨论“窗口内补冷”对碳排放的贡献，强烈建议采用上述锁存逻辑。否则无记忆 Equation 版本会在接近满罐时更频繁地小幅启停，可能高估启停次数，低估控制策略的工程可实施性。

### 10.1 当前日志状态

最近一次 `Project11.log` 未见 fatal error。可见的主要信息是：

### 10.2 控制逻辑自检

| 场景 | 应开启设备 | 应关闭设备 | 分流阀 |
|---|---|---|---|
| 工作日窗口，无负荷，水箱未满 | 冷机1/2、泵10/13、泵32、塔1/2、冷却泵1/2 | 冷机3、泵34、泵6、泵33 | Unit14 `gam=0.5` |

### 10.3 最容易出错的三点

1. `Window_time` 应使用 0/1 标记，而不是原始碳因子。若使用 Unit40，建议用 `[40,3]`。
2. Unit29 方向不能反：水箱释冷 `gam=0`，冷机3直供 `gam=1`。
3. Unit33 是负荷回水必经水泵；所有负荷供冷模式都必须开启 Unit33。

## 12. 三点可落地改进建议

1. 将 `Window_time`、`ChargeMode`、`TankMode`、`Direct3Mode`、`SOC`、`Gamma14`、`Gamma29` 输出到 Type65 或 Printer，抽查至少 3 个工作日和 1 个周末，确认窗口内不释冷、非窗口优先释冷、周末不运行。

2. 对 Unit29 做流量方向验证：水箱释冷时 `[29,2]` 应有流量且 `[29,4]` 约为 0；冷机3直供时 `[29,4]` 应有流量且 `[29,2]` 约为 0。这个检查比只看温度更能发现分流阀方向错误。

3. 做窗口比例敏感性分析：分别使用 P25、P40、P60 窗口信号，比较总碳排放、冷机3运行小时数、蓄冷罐 SOC 轨迹、供水温度越限次数和启停次数。这样可以判断当前窗口选择是否过严或过宽。
