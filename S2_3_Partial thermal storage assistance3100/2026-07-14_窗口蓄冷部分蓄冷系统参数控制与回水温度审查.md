# 蓄冷时间窗口下部分蓄冷集中供冷系统参数、控制与回水温度审查

分析日期：2026-07-14  
分析对象：`S2_3_Partial thermal storage assistance3100/Project11.dck`、`Project11.log`、`Project11.plt`、`NLF_new.csv`、`load_15min_max2.csv`、`Example_534.dat`  
系统类型：外部时间窗口驱动的部分蓄冷集中供冷系统  
设计水温：冷冻水供水 `4 degC`、设计回水 `12 degC`、设计温差 `8 K`

## 1. 先说权衡与总体结论

窗口蓄冷策略比固定夜间蓄冷更灵活，可以把冷机运行主动安排到指定低碳或低净负荷时段；代价是控制复杂度明显增加。窗口内同时存在负荷和蓄冷需求时，冷机总流量、Unit35 分流比例、Unit34/32 两条支路流量和 Unit33 回水流量必须严格一致。任何一个控制量仍沿用旧额定流量，都会立即表现为负荷回水温度异常和泵质量平衡警告。

当前模型的系统拓扑和模式划分总体正确，但参数与控制尚未形成闭合，审查结论为：**不通过，修正后可重新评审**。三个主要问题是：

1. `LoadCtrlRaw` 仍以旧总流量 `666000 kg/h` 为分母，而三台 Type110 的额定流量已改为 `430000 kg/h`。窗口内实际负荷流量只有计算需求的约 `67.8%`，这是窗口时段回水温度偏高的首要原因。
2. 非窗口水箱释冷时，Unit6 输出 `430000 kg/h`，Unit33 控制信号却为 `0.5`，只输出 `215000 kg/h`。当前日志中 Unit6 和 Unit33 分别有 `3875` 和 `3902` 个时间步质量平衡失败，直接证明该模式不守恒。
3. 冷机1仍为 `3100 kW`，冷机2为 `2000 kW`，但两台冷冻水泵均为 `215000 kg/h`，两套冷却水泵和冷却塔也都按 `2000 kW` 配置。当前系统既不是两台 3100 kW，也不是两台 2000 kW。

从当前其他参数的一致性判断，最小且合理的方案是把冷机1也改为 `2000 kW`，形成两台相同的 `2000 kW` 机组和 `430000 kg/h` 总冷冻水流量。若确实要保留 3100 kW 冷机1，则必须重新设计冷机1冷冻水泵、冷却水泵、冷却塔和 Unit14 的非对称分流比例，不建议只保留一个 3100 kW 额定容量数字。

## 3. 当前设备参数复核

### 3.1 冷机容量存在明确不一致

| 设备 | Unit | 当前额定制冷量 | 冷冻水流量 | 冷却水流量 | 判断 |
|---|---:|---:|---:|---:|---|
| 冷机1 | 9 | `11160000 kJ/h = 3100 kW` | `215000 kg/h` | `399600 kg/h` | 不匹配 |
| 冷机2 | 12 | `7200000 kJ/h = 2000 kW` | `215000 kg/h` | `399600 kg/h` | 匹配 |

`215000 kg/h` 在 `8 K` 温差下对应：

```text
215000/3600*4.19*8 = 2001.9 kW
```

因此冷机1即使额定容量填写为 3100 kW，其当前水侧只能按约 2000 kW 的设计流量运行。窗口内 Unit14 又固定为 `0.5`，说明系统实际上希望两台机组均分 `430000 kg/h`，每台得到 `215000 kg/h`。这进一步证明冷机1的 `3100 kW` 很可能是遗漏的旧参数。

冷凝侧同样不支持冷机1满负荷运行：

```text
3100 kW 冷机额定电功率 = 3100/6.147 = 504.3 kW
3100 kW 冷机排热量     = 3100+504.3 = 3604.3 kW

当前冷却塔设计散热量 = 399600/3600*4.19*(30-24.44)
                     = 2585.9 kW
```

冷却塔可以覆盖 2000 kW 冷机约 `2325.4 kW` 的排热，并有约 `11.2%` 裕量，但无法覆盖 3100 kW 冷机约 `3604.3 kW` 的额定排热。

**建议：**若本模型用于与更新后的传统蓄冷方案比较，把 Unit9 Rated Capacity 改为 `7200000 kJ/h`；COP 和归一化性能数据文件可以在第一轮暂时保留，后续再用目标 2000 kW 机型厂家数据替换。

### 3.2 水箱容量

`Example_534.dat` 中水箱容积已经是 `2850 m3`。按 `4/12 degC` 理论温差计算：

```text
E_tank = 2850*1000*4.19*8/3600
       = 26536.7 kWh
```

该理论容量与设计日最大冷量 `23518.85 kWh` 的量级匹配。但当前所有 25 个节点的初始温度仍为 `15 degC`，而控制中的暖态参考温度是 `12 degC`。建议设置 `12 degC` 初温，或增加预运行阶段使水箱达到周期稳态后再累计能耗。

### 3.3 水泵与冷却塔功率

| 设备 | Unit | 流量 | 额定功率 | 折算电功率 | 判断 |
|---|---:|---:|---:|---:|---|
| 释冷水泵 Type114 | 6 | 430000 kg/h | 145000 kJ/h | 40.28 kW | 量级合理 |
| 冷冻水泵1/2 Type114 | 10/13 | 215000 kg/h | 72764 kJ/h | 20.21 kW/台 | 与 2000 kW 单机匹配 |
| 变频泵1/2/3 Type110 | 34/32/33 | 430000 kg/h | 150000 kJ/h | 41.67 kW/台 | 量级合理，曲线待厂家数据校准 |
| 冷却水泵1/2 Type114 | 19/20 | 399600 kg/h | 174300 kJ/h | 48.42 kW/台 | 与 2000 kW 单机匹配 |
| 冷却塔风机1/2 | 18/21 | 477500 kg/h风量 | 206000 kJ/h | 57.22 kW/台 | 与约2.6 MW塔匹配 |

Type110 使用系数 `0.1、0.3、0.2、0.4`。控制信号为 `0.5` 时功率比例为 `0.35`，单泵功率约 `14.58 kW`。该曲线可以作为统一的第一版假设，但低控制量时仍有约 10% 额定功率的截距，正式能耗结论应进行泵曲线敏感性分析。

## 4. 五种运行模式的流程与控制审查

### 4.1 窗口内、无负荷、水箱未满

目标流程：

```text
冷机1/2 -> 水泵10/13 -> Unit15 -> Unit25 -> Unit35 outlet1
-> Unit34 -> 水箱 Port-2 -> 水箱 Outlet-2 -> Unit37
-> Unit31 -> Unit14 各50% -> 冷机1/2
```

当前信号：

```text
Gamma35 = 0
Pump34_CTRL = 1
Pump32_CTRL = 0
Pump33_CTRL = 0
Gamma14 = 0.5
```

判定：**控制结构正确**。前提是两台冷机均为 2000 kW，合计流量为 430000 kg/h。

### 4.2 窗口内、有负荷、水箱未满

目标是负荷优先、余量蓄冷：

```text
总流量430000 = 负荷流量 + 蓄冷流量
Pump32流量 = Pump33流量 = 负荷所需流量
Pump34流量 = 430000 - 负荷流量
Gamma35 = 负荷流量/430000
```

当前公式仍使用：

```text
LoadCtrlRaw = 1.05*LoadFlowReq/666000
```

但 Type110 的额定流量是 430000 kg/h，因此泵的实际输出为：

```text
ActualFlow = 430000*1.05*LoadFlowReq/666000
           = 0.6779*LoadFlowReq
```

负荷支路约欠流 `32.2%`。在负荷不触及控制上限时，该错误会把设计 `8 K` 温差放大到约：

```text
DeltaT_actual = 8/0.6779 = 11.80 K
```

所以供水约 4-5 degC 时，回水容易达到 15-17 degC。

判定：**当前控制错误，必须修改分母**。

### 4.3 窗口内、水箱已满且仍有负荷

当前逻辑：

```text
Chg_bySOC = 0
Gamma35 = 1
Pump34_CTRL = 0
Pump32_CTRL = 1
Pump33_CTRL = 1
两台冷机继续运行
```

这与“水箱充满后，两台冷机全部供负荷”的既定策略一致，质量流量也可以闭合。但当负荷仅为 1000-1500 kW 时，430000 kg/h 会造成明显低温差和辅助泵耗；两台冷机同时保持运行也没有必要。

建议保留该方案作为基准策略，同时增加一个优化对照方案：

- 负荷 `<=2000 kW`：只开冷机1，负荷支路约 215000 kg/h；
- 负荷 `>2000 kW`：两台冷机开启，按 `LoadCtrl` 供水；
- 不再为了“消纳全部冷机流量”而强制两台机组满流量运行。

“负荷优先”应理解为先满足建筑需求，而不是强迫负荷端接收所有可生产冷量。

### 4.4 非窗口、有负荷、水箱可用

目标流程：

```text
水箱 Outlet-1 -> Unit6 -> Unit26 -> Unit5 -> 负荷
-> Unit28 -> Unit33 -> Unit29 outlet1 -> 水箱 Port-1
```

当前参数和信号：

```text
Unit6 = 430000 kg/h
Pump33_CTRL = 0.5 -> Unit33 = 215000 kg/h
Gamma29 = 0
```

供水和回水相差 `215000 kg/h`，质量流量不闭合。日志中 Unit6 质量平衡失败3875个时间步、Unit33失败3902个时间步，与该错误完全一致。

判定：**当前控制错误**。

如果坚持固定 430000 kg/h 释冷，最小修正是：

```text
Pump33_CTRL 中 TankDischargeMode 的系数由 0.5 改为 1.0
```

如果希望降低泵耗、保持接近 8 K 温差，则推荐把 Unit6 也改为 Type110，并让 Unit6 与 Unit33 共用负荷流量控制量。两种方案的权衡见第7节。

### 4.5 非窗口、有负荷、水箱不足

目标流程：

```text
冷机1 -> Unit10 -> Unit15 -> Unit25 -> Unit35 outlet2
-> Unit32 -> Unit26 -> Unit5 -> 负荷 -> Unit28 -> Unit33
-> Unit29 outlet2 -> Unit37 -> Unit31 -> Unit14 outlet1 -> 冷机1
```

当前信号：

```text
Pump32_CTRL = 0.5
Pump33_CTRL = 0.5
Gamma35 = 1
Gamma29 = 1
Gamma14 = 0
```

Unit32 与 Unit33 都输出 215000 kg/h，和 Unit10 匹配。若冷机1改为 2000 kW，该模式控制正确。若保留冷机1为 3100 kW，则该模式仍只有约 2000 kW 的水侧能力，与额定容量不一致。

## 5. 回水温度偏高的定量诊断

按负荷文件和 NLF 第三列窗口信号对当前温度输出进行分组统计，得到：

| 工况 | 有负荷时间步 | 平均供水温度 | 最大供水温度 | 平均回水温度 | 最大回水温度 | 平均温差 |
|---|---:|---:|---:|---:|---:|---:|
| 非窗口 | 3703 | 4.45 degC | 7.51 degC | 6.25 degC | 10.51 degC | 1.80 K |
| 窗口 | 1824 | 4.11 degC | 7.53 degC | 14.84 degC | 18.38 degC | 10.73 K |

结论非常明确：

- **窗口内回水温度过高**，主因是负荷支路欠流。错误分母使实际流量只有需求的约67.8%，理论温差被放大至约11.8 K，与输出平均温差10.73 K高度一致。
- **非窗口回水温度反而过低**，主因是 Unit6 固定以430000 kg/h释冷。建筑常态负荷约0.9-1.1 MW时，设计流量只需约97000-118000 kg/h，固定大流量会把温差压到约2 K。
- 当前系统不是单纯“回水温度普遍偏高”，而是窗口内欠流、非窗口过流，两个方向同时存在。

另外，Unit27当前把 `[26,1]` 标为“负荷进水温度”，但 `[26,1]` 是合流阀2出口，尚未经过供冷总管Unit5。建议温度输出改为：

```text
负荷真实进水温度 = [5,1]
负荷真实出水温度 = [4,1]
```

这样可以排除Unit5和Unit28的管道热交换对判断的干扰。

## 6. 必须修改的控制公式

### 6.1 推荐统一基准流量

```text
TotalFlowRated = 430000
SingleFlowRated = 215000
```

### 6.2 修正负荷流量计算

将当前：

```text
LoadCtrlRaw = 1.05*LoadFlowReq/666000
LoadCtrl = HasLoad*min(0.55,max(0,LoadCtrlRaw))
```

改为：

```text
LoadCtrlRaw = 1.05*LoadFlowReq/TotalFlowRated
LoadCtrl = HasLoad*min(1,max(0.05,LoadCtrlRaw))
```

说明：

- 分母430000必须与Unit34/32/33额定流量一致；
- 上限取1，才能落实“负荷优先”，最大允许两台机组总流量进入负荷；
- 下限0.05用于避免极低负荷时Type110流量过小、管路数值不稳定；可在0.05-0.10之间测试。

修改后，其余窗口内分流式可以继续沿用：

```text
Gamma35 = min(1,WindowLoadMode*(Chg_bySOC*LoadCtrl+(1-Chg_bySOC)*1)+Chiller1BackupMode)
Pump34_CTRL = StorageChargeActive*(1-LoadWindow*LoadCtrl)
Pump32_CTRL = WindowLoadMode*(Chg_bySOC*LoadCtrl+(1-Chg_bySOC)*1)+0.5*Chiller1BackupMode
```

窗口内、水箱未满且有负荷时，将重新满足：

```text
Pump34_CTRL + Pump32_CTRL = 1
Gamma35 = Pump32_CTRL
Pump33_CTRL = Pump32_CTRL
```

### 6.3 最小改动的固定流量释冷方案

保留Unit6为Type114、额定430000 kg/h时，改为：

```text
Pump33_CTRL = WindowLoadMode*(Chg_bySOC*LoadCtrl+(1-Chg_bySOC)*1)
              + TankDischargeMode*1
              + Chiller1BackupMode*0.5
```

这样水箱释冷时Unit6和Unit33均为430000 kg/h；冷机1备用直供时仍为215000 kg/h。

优点：改动最小，完全符合当前“固定最大流量释冷”结构。  
缺点：非窗口常态负荷下温差只有约2 K，泵耗偏高，水箱温跃层容易被扰动。

### 6.4 推荐的变流量释冷方案

将Unit6改为Type110，额定流量仍为430000 kg/h，并定义：

```text
TankFlowCtrlRaw = 1.05*LoadFlowReq/TotalFlowRated
TankFlowCtrl = TankDischargeMode*min(1,max(0.05,TankFlowCtrlRaw))

DischargePump6_CTRL = TankFlowCtrl

Pump33_CTRL = WindowLoadMode*(Chg_bySOC*LoadCtrl+(1-Chg_bySOC)*1)
              + TankFlowCtrl
              + Chiller1BackupMode*0.5
```

优点：Unit6与Unit33同流量，回水温度可稳定接近12 degC，显著降低泵耗和温跃层扰动。  
缺点：需要替换Unit6并校核最小频率、Type110功率曲线和低流量收敛性。

### 6.5 增加水箱冷端出水温度判据

当前只看平均SOC和节点温度。建议最小修改为：

```text
Dch_bySOC = gt(SOC,0.1)*(1-TankEmpty)*lt([7,1],5.5)
```

`[7,1]` 是水箱Outlet-1冷端出水温度。取5.5 degC可以给Unit6和管路温升留出约0.5 K余量。若希望允许负荷供水到6.5 degC，可相应提高阈值。

普通Equation没有记忆，温度在阈值附近可能反复切换。正式模型建议用Type93锁存“TankExhausted”状态：一旦出水温度超限、SOC低于0.1或TankEmpty成立，当天保持冷机1备用直供，直到下一次有效充冷窗口再复位。

## 7. 其他控制与数据问题

### 7.1 Type9文件存在一个时间步错位风险

四个相关文件均有35041行，但：

- Unit22负荷读取跳过 `12865` 行；
- Unit39窗口读取跳过 `12864` 行；
- Unit36碳排放读取也使用另一套跳行设置。

负荷与窗口可能相差15 min，窗口边界附近会出现“窗口已切换但负荷尚未切换”或相反情况。建议统一跳行数，并用一个已知窗口起点逐点核对 `time`、`[22,1]` 和 `[39,3]`。若文件第1行代表0:00且每行间隔0.25 h，通常应保证所有同长度文件使用同一个Header Lines to Skip。

### 7.2 当前实际使用NLF第三列

```text
Window_time01 = [39,3]
```

即Unit39读取 `NLF_new.csv` 的第三列作为控制窗口。当前能耗文件命名为 `NLF60th_EC.xls`，逻辑上像是60th场景。需要在报告中明确第三列的含义，避免后续误以为第一列或第二列在控制系统。

### 7.3 Unit40 CO2_window当前未参与任何Equation

当前DCK没有任何 `[40,x]` 引用。若Unit40仅用于备查，可以删除以简化模型；若原计划用碳排放窗口控制蓄冷，则目前尚未实现该连接。

### 7.4 冷机设定温度仍只依赖初始值

Unit9/12的CHW Set Point Temperature仍是未连接输入，初始值为4 degC。建议显式连接 `T_cold_sp`，防止组件重建、导入或初始迭代时设定值丢失。

### 7.5 水箱满后的冷机台数优化

当前 `WindowChillerMode` 在水箱已满但有负荷时仍令两台冷机同时运行。建议增加台数控制：

```text
NeedTwoChillers = gt(LoadKW,1900)
```

阈值不应直接固定为2000 kW，应给性能衰减和控制裕量。第一轮可在1800-1900 kW之间测试。若需要保证基准策略完全不变，则至少把“两台继续运行、全流量送负荷”明确写为研究假设，并与分级启停方案做敏感性比较。

| Unit10/13质量平衡失败 | 各2时间步 | 模式切换瞬态 |
| Unit19/20质量平衡失败 | 各5时间步 | 冷机切换或初始迭代 |
| 全系统不收敛 | 30时间步 | 部分时间步采用最后迭代值 |
| Type31管道容量警告 | 6个管道 | 时间步远大于管道停留时间 |
| 冷机性能表越界 | 两台各46次 | 低冷却水温工况被钳位 |

当前累计结果为：冷机约 `139.38 MWh`、冷却塔约 `62.29 MWh`、水泵约 `152.09 MWh`、总电耗约 `353.76 MWh`。由于近3900个时间步存在水箱释冷质量不平衡，这组能耗不能用于与传统模式比较，也不能据此得出窗口蓄冷更节能或更低碳的结论。

## 9. 推荐修改顺序

### 第一优先级：恢复物理一致性

1. 确认统一采用两台2000 kW；将Unit9容量改为7200000 kJ/h。
2. 将`LoadCtrlRaw`分母由666000改为430000，上限由0.55改为1。
3. 固定流量释冷方案下，将`TankDischargeMode*0.5`改为`TankDischargeMode*1`。
4. 统一负荷和窗口文件的Header Lines to Skip。

验证标准：Unit6、Unit33质量平衡失败必须从约3900次降为0。

### 第二优先级：保证供水品质和切换稳定

1. `Dch_bySOC`增加 `[7,1] < 5.5 degC`。
2. 用Type93或等效状态模块锁存水箱耗尽状态。
3. 把温度输出改为 `[5,1]` 和 `[4,1]`。
4. 显式连接两台冷机的4 degC设定温度。

验证标准：有负荷时供水温度建议不高于6 degC，窗口内平均回水温度应接近11-12 degC。

### 第三优先级：降低能耗

1. Unit6改Type110，与Unit33共用TankFlowCtrl。
2. 水箱满后按负荷分级启停一台或两台冷机。
3. 用厂家泵曲线替换统一的0.1/0.3/0.2/0.4系数。
4. 对固定全流量和负荷跟随两套方案做典型日与全季对比。

## 11. 最终评价与三点优化见解

1. **当前回水温度问题本质上是控制量基准没有随设备缩容同步更新。** 旧分母666000与新泵430000混用，使窗口内负荷侧天然欠流约32%，不是建筑负荷或Type682本身异常。
2. **窗口蓄冷系统必须同时管理能量和质量流量。** 负荷优先分配在能量逻辑上成立，但只有Unit35、Unit34、Unit32、Unit33四者使用同一个总流量基准时，TRNSYS水力闭环才成立。
3. **水箱满后把全部冷机流量送往负荷是可定义的基准策略，但不是推荐的最终策略。** 更合理的控制是按负荷决定冷机台数和流量，让“负荷优先”表现为满足需求，而不是强制消纳冷量。

本报告的局限性在于尚未对修正后的工程重新运行。冷却塔和泵功率目前主要依据现有模型比例缩放，正式设备选型仍需厂家性能曲线、扬程和效率数据支持。
