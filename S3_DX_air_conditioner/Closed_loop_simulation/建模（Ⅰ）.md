# 一、先明确闭环仿真的物理逻辑

以一个房间 `S_bgs1` 为例，分体式空调的真实过程是：

```text
房间空气 26~28°C、某个湿度
        ↓ 回风
室内机蒸发器
        ↓ 降温、除湿
送风回房间
        ↓
房间温度、湿度下降
```

在 TRNSYS 里对应关系是：

```text
Type56 输出房间空气状态：
T_zone、RH_zone、W_zone

Type954 接收：
T_return = T_zone
RH_return = RH_zone
W_return = W_zone
T_ambient = 室外干球温度
W_ambient = 室外含湿量
RH_ambient = 室外相对湿度
y_cool = 温控信号

Type954 输出：
Q_sensible_c
Q_latent_c
Power
Flow_cond

反馈给 Type56：
负的显热增益 = -Q_sensible_c
负的湿量增益 = -凝结水量
```

注意这里的核心不是把 Type56 的 `QCOOL` 接给 Type954，而是把 **Type56 的室内状态** 接给 Type954，再把 **Type954 的实际制冷效果** 接回 Type56。

# 三、第二阶段：在 Type56 里增加房间状态输出

# 四、第三阶段：不要再让 S_bgs1 用理想冷源

你现在 `S_bgs1` 的 airnode 里有：

```text
COOLING = COOL001
```

而 `COOL001` 是无限冷源：

```text
POWER=999999999
```

如果你保留它，同时又把 Type954 的制冷量反馈给 Type56，就会变成：

```text
理想冷源在制冷
Type954 也在制冷
```

这就是**重复制冷**，结果没有物理意义。

所以对闭环试验房间 `S_bgs1`，要先取消理想冷源。

## 操作步骤

在 TRNBuild 里找到：

```text
Zone / Airnode S_bgs1
```

在 `Regime` 中找到：

```text
COOLING = COOL001
```

对 `S_bgs1` 暂时去掉这条，或者给它换成一个始终关闭的 Cooling，比如：

```text
COOLING OFF
```

更推荐你新建一个冷源：

```text
COOLING COOL_OFF
ON=SCHEDULE 0
POWER=0
```

然后让 `S_bgs1` 使用 `COOL_OFF`。

这样做的意义是：

```text
S_bgs1 的温度和湿度不再被 Type56 理想冷源强制维持，
而是由 Type954 的实际制冷量决定。
```

其他房间暂时不要动，避免模型一次变化太多。

# 五、第四阶段：在 Type56 里创建“分体空调反馈增益”

这里有两种方法。

## 方法 A：用送风状态反馈

也就是把 Type954 的送风温度、送风湿度、送风量接回 Type56 的 ventilation。

这个方法看起来很物理，但在你的模型里不太推荐作为第一步，因为你现在每个 airnode 已经有 `VENT_office`、`VENT_cesuo`、`VENT_connect` 这些新风/通风对象。Type56 通常一个 airnode 只方便挂一个 ventilation 对象，直接替换会影响原来的新风负荷。

## 方法 B：用负的显热增益 + 负的湿量增益反馈

我建议你先用这个方法。它最适合你现在的模型。

逻辑是：

```text
Type954 计算出这个房间空调实际提供的显冷量 Q_sensible_c
→ 作为负的 convective gain 输入 Type56

Type954 计算出凝结水量 Flow_cond
→ 作为负的 humidity gain 输入 Type56
```

也就是：

```text
房间得热：人员、照明、设备、太阳辐射、通风
房间失热：Type954 的显冷量
房间得湿：人员、新风、渗透
房间除湿：Type954 的凝结水量
```

这条路线和你当前模型最兼容。

# 六、第五阶段：在 TRNBuild 里添加 DX 空调负增益

以 `S_bgs1` 为例。
[具体gain添加步骤](添加Gain)
## 1. 新建一个 Gain

在 TRNBuild 里找到：

```text
Gains / Losses
```

新建一个 gain，比如命名为：

```text
GAIN_DX_S_bgs1
```

设置为：

```text
CONVECTIVE = INPUT
RADIATIVE  = 0
HUMIDITY   = INPUT
ELPOWERFRAC = 0
ABSOLUTE
CATEGORY = OTHER
```

含义是：

```text
CONVECTIVE = 分体空调从房间空气中移除的显热
HUMIDITY = 分体空调从房间空气中移除的水分
```

这里要注意单位：

Type954 的 `Q_sensible_c` 输出通常是：

```text
kJ/h
```

而 TRNBuild 里的内部增益通常按：

```text
W
```

所以要做单位换算：

```text
Q_DX_sens_W = - Q_sensible_c / 3.6
```

因为：

```text
1 W = 3.6 kJ/h
```

湿量不用除以 3.6。Type954 的凝结水流量通常是：

```text
kg/h
```

所以：

```text
M_DX_dehum = - Flow_cond
```

如果你不用凝结水量，也可以用潜冷量近似换算：

```text
M_DX_dehum = - Q_latent_c / 2450
```

其中 `2450 kJ/kg` 是水蒸发潜热的近似值。但更推荐用 Type954 的凝结水输出。

## 2. 把这个 Gain 加到 S_bgs1

在 `S_bgs1` 的 Regime 里，保留原有人员、照明、设备：

```text
GAIN_people
GAIN_light
GAIN_equip
```

再增加一条：

```text
GAIN = GAIN_DX_S_bgs1
```

这样 `S_bgs1` 就能接受外部空调的实际冷量反馈。

# 七、第六阶段：在 Studio 里放置 Type954

现在回到 Simulation Studio，给 `S_bgs1` 放一个 Type954。

建议先命名为：

```text
DX_S_bgs1
```

## Type954 参数建议

以单速分体空调为例：

```text
Humidity mode = 2
Total air flow rate = 额定送风量，例如 300 L/s，先固定
Rated air flow rate = 同上，例如 300 L/s
Rated total cooling capacity = 按房间峰值负荷选
Rated sensible cooling capacity = Rated total × SHR
Rated cooling power = Rated total / COP
Minimum %RH for latent heat transfer = 50~60，或先用 20 测试
Auxiliary heat mode = 0，如果只做制冷
```

如果只做制冷，制热参数可以保留默认，但不要让 heating signal 开启。

## 容量怎么选？

先从你 Type56 的 `QCOOL + QLATD` 结果中找 `S_bgs1` 的峰值负荷。

假设某房间峰值总冷负荷为：

```text
Q_peak = 60 kW
```

那么分体空调额定总冷量不要刚好取 60 kW，建议取：

```text
Q_rated = 1.1~1.2 × Q_peak
```

也就是：

```text
66~72 kW
```

但这里我要提醒你：如果你说的是“每个房间一个分体式空调”，普通房间的单台容量通常不会几十上百 kW。你当前模型里 `S_bgs1` 面积很大，`REFAREA=800 m²`，这其实更像一个大功能区，而不是一个普通小房间。所以严格说，它不是“一个房间一台普通壁挂机”的尺度，更像“一个大办公室区域配置多台分体机/多联机室内机的等效模型”。

论文里建议写成：

```text
Each thermal zone is served by an equivalent split-type DX air-conditioning unit.
```

不要写成：

```text
Each small room is served by one residential split air conditioner.
```

否则设备容量会显得不现实。

# 九、第八阶段：建立温控器

不要一直让 Type954 开机。你需要一个控制器。

推荐最简单的控制逻辑是：

```text
工作时间内：
    当 T_zone > 26.5°C 时，空调开
    当 T_zone < 25.5°C 时，空调关

非工作时间：
    空调关
```

这个 25.5~26.5°C 是死区，目的是避免频繁启停。

## 推荐用 Type2 控制器

在 Studio 里添加：

```text
Controllers → Differential Controller → Type2
```

大概设置为：

```text
Upper dead band / 上限 = 26.5°C
Lower dead band / 下限 = 25.5°C
```

输出为：

```text
0 或 1
```

然后再乘以工作时间表：

```text
y_cool_S_bgs1 = work_sch × y_type2
```

如果你用 Equation，可以写成概念形式：

```text
y_cool = work_sch * controller_output
y_fan  = y_cool
y_heat = 0
```

不要用没有死区的控制：

```text
Tzone > 26 就开
Tzone < 26 就关
```

这种会在 26°C 附近疯狂跳变，尤其你现在如果还是 1 h 时间步，结果会很难看。

# 十、第九阶段：把 Type954 输出反馈给 Type56

Type954 输出里关键的是：

```text
Output 7  = Q_sensible_c
Output 8  = Q_latent_c
Output 13 = compressor + indoor fan + outdoor fan power
Output 14 = COP
Output 20 = condensate temperature
Output 21 = condensate flow rate
```

在 Studio 里加一个 Equation：

```text
Qdx_sens_S_bgs1 = -[DX_S_bgs1,7]/3.6
Mdx_dehum_S_bgs1 = -[DX_S_bgs1,21]
Pdx_S_bgs1 = [DX_S_bgs1,13]/3600
```

解释：

```text
Qdx_sens_S_bgs1
```

是传给 Type56 的显热负增益，单位 W。

```text
Mdx_dehum_S_bgs1
```

是传给 Type56 的除湿量，单位 kg/h。

```text
Pdx_S_bgs1
```

是空调电功率，单位 kW。因为 Type954 功率通常为 kJ/h，所以除以 3600 得到 kW。

然后把：

```text
Qdx_sens_S_bgs1
```

连接到 Type56 中 `GAIN_DX_S_bgs1` 的 convective input。

把：

```text
Mdx_dehum_S_bgs1
```

连接到 Type56 中 `GAIN_DX_S_bgs1` 的 humidity input。

这一步完成后，闭环就真正形成了：

```text
Type56 → Type954 → Equation → Type56
```

# 十一、第十阶段：把时间步长改小

你现在 `Untitled_imported.dck` 里时间步是：

```text

```

也就是 1 小时。

这对分体式空调 on/off 闭环太粗了。单速空调如果 1 小时内全开，很容易过冷；如果全关，又容易温度飙升。建议改成：


也就是 15 min。

如果还是震荡，可以进一步用：

```text

```

也就是 6 min。

但一般论文级建筑能耗仿真，15 min 已经够用了。

# 十二、先跑单房间闭环时，你应该看哪些结果？

不要一上来只看总能耗。先看单房间是否物理合理。

建议输出：

```text
T_S_bgs1
RH_S_bgs1
y_cool_S_bgs1
Q_sensible_Type954
Q_latent_Type954
Flow_cond_Type954
P_Type954
COP_Type954
Qdx_sens_feedback
Mdx_dehum_feedback
```

判断标准：

## 1. 温度是否合理

工作时间应该大致围绕：

```text
25.5~26.5°C
```

上下波动。

如果温度长期高于 28°C：

```text
设备容量不足，或控制没有开机，或反馈没有接进去。
```

如果温度快速降到 20°C 以下：

```text
设备容量过大，时间步过长，或者没有做启停死区。
```

## 2. 湿度是否合理

工作时间 RH 建议关注：

```text
50%~65%
```

如果 RH 长期超过 70%：

```text
潜热处理不足，或者除湿反馈没有生效。
```

如果 RH 被拉到很低，比如 30% 以下：

```text
除湿过强，Minimum %RH for latent heat transfer 设置过低，或负湿量输入过大。
```

## 3. 空调启停是否合理

如果 `y_cool` 每个 timestep 都在 0/1 之间疯狂跳：

```text
死区太小，时间步太大，设备容量过大。
```

可以调整为：

```text
开机：T > 27°C
关机：T < 25.5°C
```

或者用更小 timestep。

# 十三、跑通 S_bgs1 后，怎么扩展到其他房间？

按这个顺序：

```text
1. S_bgs1 办公室
2. S_hys1 会议室
3. S_cs1 厕所
4. S_zl1 走廊
```

这四个代表性热区跑通后，再扩展到同类区域。

你当前输出里已经对四类功能区做了汇总：

```text
All_Office
all_hys
all_wc
All_zou
```

所以后续可以有两种建模方式。

## 方式 1：每个 airnode 一个等效 Type954

优点：

```text
最严格，能看每个房间温湿度。
```

缺点：

```text
接线多，计算慢，容易不收敛。
```

适合最终精细模型。

## 方式 2：每类房间做代表房间，再乘以数量

例如：

```text
S_bgs1 代表办公室
S_hys1 代表会议室
S_cs1 代表厕所
S_zl1 代表走廊
```

能耗计算：

```text
P_office_total = P_S_bgs1 × 办公室数量修正系数
P_meeting_total = P_S_hys1 × 会议室数量修正系数
...
```

优点：

```text
模型清晰，适合论文策略比较。
```

缺点：

```text
不能反映所有房间朝向差异。
```

如果你的重点是系统策略、碳排放、运行能耗，而不是逐房间舒适性，我更推荐方式 2。不要为了“看起来精细”把模型堆成一坨线团。

# 十四、厕所和走廊要特别注意

厕所不建议简单理解成普通分体空调房间。厕所通常有较大排风量，你的模型里 `VENT_cesuo` 已经明显比办公室大：

```text
AIRCHANGE=SCHEDULE 4.5*Vent_office
```

如果厕所也放分体空调，要特别检查：

```text
新风 / 排风带来的湿负荷
除湿量
RH 是否长期偏高
空调容量是否被排风负荷吞掉
```

现实中厕所一般更依赖排风和新风处理，不一定每个厕所单独配普通分体式空调。论文里如果把厕所也作为独立 DX 空调区，需要解释清楚这是“等效区域空调模型”。

走廊也类似。走廊可能不是每段都放分体机，而是由相邻房间或集中系统间接处理。你可以保守处理为：

```text
办公室、会议室设 Type954；
厕所、走廊保持理想冷源或设置独立通风负荷；
后续做敏感性分析。
```

如果你坚持全楼所有热区都分体式空调，也可以，但论文里要解释为“等效局部分散式空调系统”。

# 十八、我对你当前模型的建议判断

你现在已经完成了最难的前半步：**Type56 建筑模型和负荷输出已经跑通**。下一步不要再纠结“Type56 负荷怎么接 Type954”，因为那不是闭环的核心。

真正要做的是：

```text
不要把 QCOOL 当作 Type954 的输入；
要把 Tzone、RHzone、Wzone 当作 Type954 的输入；
再把 Type954 的实际制冷/除湿效果反馈给 Type56。
```

这句话非常关键。

如果你用 `QCOOL / Qavail × Pfull` 算能耗，那是负荷后处理模型；如果你用 `Tzone/RH/W → Type954 → 冷量/除湿量 → Type56`，这才是闭环仿真。

我的建议是：你下一步先只做 `S_bgs1` 一个办公室闭环。跑通后，把生成的新 `.dck` 或 `.b18` 发我，我可以继续帮你检查接线、单位和反馈符号有没有错。
